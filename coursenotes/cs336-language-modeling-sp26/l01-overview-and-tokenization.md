# 第 1 讲 · 课程概览与分词

> **Stanford CS336 语言模型从零构建 · L01** ｜ 讲者 Stanford Online ｜ 79 分钟 ｜ [原视频](https://www.youtube.com/watch?v=JuoVZkPBiKk)

**核心结论**

CS336 的核心理念是“from scratch”：通过亲手实现分词器、Transformer、训练栈、系统优化、缩放定律、数据管线和对齐算法，真正理解语言模型如何工作。课程承认前沿模型的规模与成本难以复制，因此明确区分可迁移的“机制/思维”和较难跨规模迁移的“直觉”，并把效率作为贯穿始终的主线。课程同时强调开放模型生态对教学的重要性：开放权重、论文、代码和数据让外界得以窥见前沿模型的部分构造。本次课的后半部分从字符级、字节级、词级分词方案的缺陷出发，引出 BPE 的数据驱动合并算法，并说明分词器仍需满足序列抽象与自适应计算等需求。

## 为什么从零构建：抽象、前沿模型与教学取舍 [02:22 - 05:38]

讲师给出的核心问题是：研究者正在与底层技术脱节。大约 2016 年，AI 研究者还会自己实现并训练模型；2018 年，大家下载 BERT 等预训练模型做微调；今天，很多人只需 prompt API 模型。Prompting 本身没有错，抽象化总体也是好事，但抽象是“有漏洞的”（leaky abstractions）：当模型无法完成某个任务时，如果只会 prompt，就没有进一步的手段。若要做基础研究，只在 prompt 层面工作会极大限制可探索的设计空间；真正的基础研究需要“掀开整个技术栈”。

![解释开设课程原因的幻灯片，对比2016至今天研究人员与底层技术的脱节](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0003_00-03-58.jpg)

但“从零构建”面临现实障碍：语言模型已经工业化。前沿模型极其昂贵，GPT-4 据称训练成本约 1 亿美元，如今前沿成本可能是十亿美元量级（讲师称这是推测）；大实验室的 GPU 数量巨大，而且模型细节不公开。GPT-4 技术报告明确写道，出于竞争格局和安全影响，不披露架构、硬件、训练算力、数据构造、训练方法等细节。

![GPT-4技术报告截图，高亮说明因竞争和安全考虑未公开架构、硬件等细节](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0004_00-05-26.jpg)

因此课程会构建小语言模型，但讲师提醒：小模型不一定代表前沿模型。

## 小模型与前沿模型的差异 [05:54 - 07:07]

讲师给出两个例子说明规模会改变结论。

第一，计算花在哪里会随规模变化。在小规模下，MLP 层约占 44% 的 FLOPs；扩展到 175B 参数时，这一比例可到约 80%。因此在小规模上优化 attention，未必能在大规模上获得同样收益。

第二，能力会随规模“涌现”。在一些零样本/少样本任务上，小模型表现几乎不提升，只有达到某个临界规模后才突然改善。若只在小规模实验，可能观察不到这些现象。

![模型能力随规模涌现的四个任务表现折线图（Wei+ 2022）](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0005_00-06-35.jpg)

## 三类可迁移知识：机制、思维与直觉 [07:16 - 09:09]

课程把知识分为三类：

- **Mechanics（机制）**：事物如何工作，例如 Transformer 是什么、模型并行如何运作。
- **Mindset（思维）**：如何构建语言模型，如何榨干硬件性能、严肃对待缩放。
- **Intuitions（直觉）**：哪些数据和建模决策会带来好的准确率。

讲师认为，机制和思维可以较好教授，并且能迁移到更大规模；直觉则不一定跨规模迁移，往往需要在真正的大规模环境中获得。课程会反复强调 profile、benchmark 和效率优化。

![课程总结幻灯片：三类可迁移知识（机制、思维、直觉）](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0006_00-07-56.jpg)

关于直觉，讲师举了 SwiGLU 激活函数的例子：论文结论非常坦率地表示，他们不解释这些架构为何有效，而把成功归因于“神的恩典”。这说明有些建模决策只能通过实验和经验获得。

## 正确理解 The Bitter Lesson：效率与可扩展算法 [09:15 - 11:33]

讲师指出一个常见误解：认为“规模就是一切，算法不重要”。正确的理解应是：**能够随规模扩展的算法才重要**。可以用一个简单框架表示：

$$
\text{accuracy} = \text{efficiency} \times \text{resources}
$$

其中 efficiency 是输出/输入，resources 是投入。效率在大规模下更重要：小实验慢一倍或许可以多等一倍时间，但大规模训练成本可能是数亿美元，5% 的提升都可能是大事。

![The bitter lesson核心观点幻灯片，强调算法效率的重要性](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0008_00-10-35.jpg)

经验上，OpenAI 2020 年的一篇论文显示，2012—2019 年间 ImageNet 上有约 44 倍的算法效率提升；硬件当然也进步了，但算法改进与硬件进步相乘，才带来效率与准确率的大幅提升。

因此课程的总框架是：**在给定数据和算力预算下，构建最好的模型**。预训练阶段通常假设数据远多于算力；如果处于数据受限环境，或者拥有大量 B200，则可能变成数据受限。

## 语言模型简史：从 N-gram 到规模化 [11:36 - 15:35]

语言模型并非新事物。Shannon 在 1950 年代就用语言模型测量英语的熵；N-gram 模型长期用于机器翻译和语音识别，虽然不是完整系统，但对生成流畅文本很重要。

现代语言模型的谱系主要来自神经架构。讲师列举了 2010 年代的关键组件：

- LSTM
- Bengio 等人 2003 年的首个神经语言模型（前馈网络，看很小上下文）
- Sequence-to-sequence 建模
- Adam 优化器
- 为机器翻译开发的 attention 机制
- Transformer 架构
- Mixture of Experts
- 模型并行

![语言模型发展历程幻灯片，展示前神经网络时代的熵测量研究](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0009_00-11-54.jpg)

![2010年代神经网络关键组件列表，涵盖LSTM、Seq2Seq、Adam、注意力机制、Transformer、MoE及模型并行](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0010_00-13-14.jpg)

到 2010 年代后期，ELMo、BERT 展示了“大规模文本预训练 + 下游任务微调”的威力；T5 把一切建模为 text-to-text，已经预示了“prompt 进、response 出”的范式。OpenAI 则拥抱缩放：GPT-2 展示流畅文本与零样本迹象，缩放定律提供了可预测性，GPT-3 展示上下文学习。Google 的 PaLM 规模巨大但训练不足；DeepMind 当时尚未与 Google 整合，已研究计算最优缩放定律。

![早期基础模型（ELMo、BERT、T5）及拥抱规模化（GPT-2、GPT-3、PaLM）的发展脉络](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0011_00-14-33.jpg)

## 开放模型生态为何重要 [15:35 - 17:28]

GPT-3 之后出现了一批复现尝试，但早期开放模型并不强：有的组织算力有限，模型规模不大；Meta 的第一个 LLM 是 175B 参数，但遇到不少硬件问题；Hugging Face 的 Big Science 项目也属于早期尝试。

最近三年，开放模型生态明显变化：Meta 的 Llama 系列、Mistral，以及 DeepSeek、Qwen、Kimi、GLM、MiniMax、小米 MIMO 等模型不断出现。开放权重模型正在接近闭源模型；根据不同评测，可能略落后或可比，但已经是工业界广泛使用的可信模型。

![开源模型列表（Llama、Mistral、DeepSeek、Qwen等）及GLM-5论文摘要弹窗](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0012_00-15-52.jpg)

更进一步，AI2 的 Olmo、NVIDIA 的 Nemotron，以及讲师参与的 Marin 项目，不只开放权重，还开放论文、代码和数据，使外界能更完整地理解模型如何构建。讲师强调：没有这些开放模型，这门课很难开设；虽然 Qwen 等论文仍缺少数据配比等关键细节、无法完全复现，但比什么都没有好得多。开放性是信任与创新的重要基础。

## 语言模型定义的演变与不变的基础 [17:32 - 19:07]

过去十年，“语言模型是什么”发生了变化：

- 2018 年（BERT）：用来微调的东西。
- 2020 年（GPT-3）：用来 prompt 的东西。
- 2022 年（ChatGPT）：可以对话的东西。
- 2026 年（agents）：可以自主行动的东西。

![语言模型定义演变及核心基础不变的幻灯片](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0014_00-18-31.jpg)

但基础并没有大变：仍然在 GPU 和 kernel 上构建，仍用梯度或随机梯度类方法优化，仍有 Transformer 和 attention。变化的是规格：如今要求更长上下文，因此推理效率更加重要。讲师说，好消息是课程不需要完全重写，只需更新部分章节；这些基础至少目前仍然成立。

## 课程大纲总览与基础模块、作业一 [27:17 - 35:53]

课程分为五个部分，对应五次作业：basics、systems、scaling laws、data、alignment。贯穿始终的原则是效率：资源包括数据和硬件（算力、内存、通信带宽），目标是在固定资源下构建最好的模型。

![课程大纲的Python伪代码，展示作业1-5的主题及效率核心原则](/coursenotes/cs336-language-modeling-sp26/l01-overview-and-tokenization/kf_0020_00-27-22.jpg)

**Basics（前两周）** 的目标是能从头训练一个语言模型：分词、定义架构、实现优化器和训练器。

**分词**决定模型操作的“原子”。形式上，tokenizer 在原始输入（字节）和整数序列（token）之间转换；概念上是对文本的分段。课程会讲 BPE（Byte Pair Encoding），直觉上把输入拆成频繁出现的块。从效率角度看，分词把长字节序列压缩成更少的 token；更重要的是，它允许**自适应计算**：有些地方字节很多但应压缩成一个 token，有些稀有或有趣的部分则应保留为多个 token。

讲师提到，他每年都希望不再教分词，梦想是端到端直接操作字节；H-Net 等工作看起来有希望，但尚未扩展到前沿规模，而前沿模型仍在使用 tokenizer，所以仍值得教。

**架构**方面，大家可能已在 CS224N 见过 Transformer，但这些年有许多改进：激活函数、位置编码、归一化、减少 $O(n^2)$ attention 计算的方法、状态空间模型/线性 attention（如 Mamba、Gated DeltaNet）及其与 attention 的混合、MLP 中的 Mixture of Experts，以及层数、头数、隐藏维度、专家数等形状参数。后者看似只是超参数，但在缩放语境下影响巨大。

**训练**方面涉及损失函数（默认下一 token 预测，也有预测多个 token 的做法）、优化器（Adam，以及越来越多使用的 Muon）、初始化、学习率调度、正则化、batch size、MoE 特有技术。讲师强调，这些不是随便试的超参数：是否系统地设置它们，决定了一次训练是崩溃无用，还是达到 state of the art。

**作业一**要求实现 BPE tokenizer、Transformer、损失函数、优化器和完整训练栈；做资源核算，理解 FLOPs 花在哪里；在 TinyStories、OpenWebText 等数据集上训练模型；并通过排行榜尽可能快地降低 perplexity。

讲师总结说，tokenizer、建模和训练看似分离，实际都在平衡三件事：**表达力**（表示数据复杂性）、**训练稳定性**（让参数和梯度范数处于“金发姑娘”区间，不爆炸也不消失）和**效率**（在硬件上跑得快）。很多架构决策都是在“更快”和“效果是否一样好”之间做权衡。

## 系统模块与作业二：kernel、并行与推理 [35:53 - 45:09]

系统部分的目标是榨干硬件性能，内容包括 kernel、多 GPU 并行和推理。

**资源核算**是基础：跟踪 FLOPs 和内存去向。例如训练一个 7B 模型、1 万亿 token，粗略需要

$$
6 \times N \times D
$$

其中 $N$ 是参数量，$D$ 是 token 数。课程会解释这个公式从何而来。

**硬件**方面，关键点是内存和计算不在同一个地方：必须把参数或激活从内存搬到计算单元，算完再搬回，数据移动往往是瓶颈。例如 B200 在 BF16 下约 2.25 PFLOPS，内存带宽约 8 TB/s；课程会用这些数字做计算，分析不同算法需要多久。Roofline 分析用于判断一个计算是受算力还是内存带宽限制；一般来说常受内存限制。之后还会讲 benchmark 与 profiling。

一个 DGX B200 有 8 个 GPU，通过 NVLink 连接；上千 GPU 时会有多台这样的机器，通过 InfiniBand 或 Ethernet 连接。

**Kernel** 是运行在 GPU 上的函数。即使用普通 PyTorch，PyTorch 原语也会启动内置 kernel；但某些计算可以写自定义 kernel 让 GPU 更快。核心原则仍是**最小化数据移动**。例如计算两个操作时，朴素做法是从 HBM 读、算、写回，再读、算、写回，数据来回两次；**算子融合**（fusion）可以一次读入、完成两个计算、一次写回。**Tiling** 是同一思想的更复杂变体。课程会接触 GPU 的一些特殊细节，并尝试写 kernel。

当有数千 GPU 时，最小化数据移动的原则不变，但跨 GPU 移动数据更贵。课程会讲 gather、reduce、all-reduce 等集合通信操作，用它们理解分布式训练。模型参数、激活、梯度、优化器状态需要分片到多 GPU，并把正确数据送到正确节点。分片方式包括按数据、模型、层、序列、专家切分，各有取舍。

**推理**越来越重要：不仅用于聊天，也用于强化学习的 rollout、测试时计算、合成数据生成和评测。推理分两阶段：**prefill** 把 prompt 的所有 token 前向计算，建立 key-value 对，类似训练；**decode** 一次生成一个 token，很快变成内存受限，这是推理困难的原因。加速方法包括剪枝、量化、蒸馏、**投机解码**（用便宜模型先猜多个 token，再用完整模型并行验证），以及推理专用 kernel。服务场景中请求到达时间不同，如何 batching 也是问题；训练中 batch 则更可预测。

**作业二**会要求用 Triton 实现 kernel，并进行并行训练。细节可能因助教调整而变化，但覆盖大致相同内容。讲师推荐 Google 的《How to Scale Your Model》：虽然以 TPU 为主，但 roofline、Transformer 数学等高层概念相通，且有新章节讲 GPU。

## 缩放定律与作业三 [45:09 - 53:27]

缩放定律部分面对的问题是：如果你有 $10^{25}$ FLOPs（数千万美元级算力），应该训练什么模型？这个规模下不能像小实验那样随意调参，因为可能只负担得起一次训练。

关键概念转变是：不要只想“训练一个模型”，而要想**缩放配方**（scaling recipe）——一个从 FLOPs 预算映射到超参数配置的映射。做法是：在小规模跑一系列实验，拟合缩放定律，预测目标规模的 loss。这样可以用小实验优化大模型配方，并在真正训练前预测 loss；讲师半开玩笑地说，这也可以用来向投资人证明“小实验表明我能做出 GPT-5 级别模型”。

缩放定律不是自然规律，不会自动成立；需要精心构造可外推的配方。例如学习率随规模保持不变还是下降、batch size 如何增长，都必须定义。为了实现可预测的缩放，需要**超参数迁移**：小规模用的超参数要么可直接用于大规模，要么是规模的可预测函数。因此，**可预测性至少和最优性一样重要**。

经典缩放定律包括 Kaplan 等人和 Chinchilla 的工作：给定 FLOPs 预算，在不同模型大小间扫描，选择最优者，再拟合“预算—参数量”曲线。经验规则是训练 token 数约为参数量的 20 倍：70B 模型约训练 1.4 万亿 token。实际会随数据集和架构变化；而且该规则未考虑推理成本。现在很多模型更小但训练 token 远超计算最优，因为推理时希望模型更小。

讲师提到 Marin 项目的做法：预注册结果。他们在不同算力预算拟合缩放定律，并对 $10^{22}$ FLOPs 的训练做预测，实际训练可在 Marin 网站跟踪；如果预测匹配，就说明缩放定律很有用。

**作业三**提供训练 API：学生提交超参数配置，系统返回 loss。课程离线训练了一批模型并做缓存，模拟“可以大量训练”的环境。学生应拟合缩放定律、外推，并在给定预算下提交配置，最终评估模型表现。这模拟了真实中高压力、高预算的决策场景，但风险很低。

## 数据模块与作业四 [53:38 - 60:20]

数据部分回答“用什么训练模型”。讲师认为数据质量基本决定模型好坏；数据也反映你希望模型做什么：多语言、对话、长程 agentic coding 等。

先讲**评测**，因为评测定义你希望模型具备的能力。评测分内部指标和外部指标：内部指标用于模型开发，重视跨规模平滑、可预测、相对性能，perplexity 是捕捉模型内在质量的好指标，且不易被 benchmark 刷分；外部指标面向客户或审稿人，重视生态效度。两类指标目的不同，不应混淆。评测数据最好来自互联网之外以避免污染；语言模型号称通用，因此需要多样化的评测集，可以平均成单一数字，但平均会掩盖差异。

数据不会从天而降，需要主动整理。来源包括网页、书籍（有争议）、论文、GitHub 代码等。数据不仅是文本，而是 HTML、PDF、代码目录，需要处理成可用文本。法律问题也重要：训练版权数据是否属于合理使用、是否需授权；很多 GitHub 代码没有许可证，如何解释需要选择。

数据处理步骤包括：转换（非文本转文本）、过滤（去掉糟糕的 Common Crawl 文档）、去重、多来源混合，以及近年来的合成数据（改写真实数据以更接近下游任务或更像维基百科）。数据可用于预训练、中期训练（预训练末尾的高质量数据，包括长上下文数据，如大型代码库或书籍）和后训练（对话、带工具调用的 agent trace）。

**作业四**从非常原始的网页抓取语料开始，完成过滤、去重、清洗。讲师说这可能是“脏活”，但这是从零构建语言模型的重要部分，需要完整体验。

## 对齐模块与作业五 [60:20 - 62:54]

到目前为止都是全监督：预测下一个或下几个 token。此时模型应该已经不错，但还可以用**弱监督**改进。弱监督有用的原因是：有时“批评”比“生成”更容易——未必总有“这个 prompt 的正确答案”数据，但可以定义“什么是好”。

基本模板是：模型生成回答，由人类、验证器或 LM judge 打分，再更新模型使其偏好更好的回答。可以用 PPO、GRPO 等 RL 算法，也可以用更简单的偏好数据方法 DPO。

RL 的挑战是不稳定、难调。讲师个人倾向于尽可能停留在全监督，最后才做 RL。大规模 RL 还有很多系统挑战：需要推理服务器和训练服务器；推理服务器生成 rollout，若涉及代码执行环境，还要编排；worker 落后会产生 off-policy 问题，需要在 on-policy 性与吞吐之间权衡。

**作业五**去年是实现 DPO 和 GRPO，并在数学 benchmark 上跑通；今年具体内容仍在决定，可能更贴近现实。

## 效率作为贯穿主线 [62:54 - 64:46]

讲师再次回到效率：效率可以是数据效率或计算效率。你拥有数据、硬件（算力核心、内存、通信带宽），目标是在固定资源下按某种评测构建最好的模型。

用这个视角看课程各部分：

- **系统**：计算效率。
- **分词**：直接处理字节在当今架构下计算效率很低，分词主要是提高计算效率。
- **模型架构**：许多改动是为了减少内存或 FLOPs，很多受推理速度需求影响。
- **数据过滤**：固定算力下，在坏数据上更新梯度会挤占好数据的时间。
- **缩放定律**：本质上是用小模型做有效的超参数调优。

如果未来变成数据受限，具体决策可能变化，但“思考方法的效率”仍是课程想教的心态。

## 分词：从字符串到 token [65:07 - 72:55]

原始文本是 Unicode 字符串；语言模型则在 token 序列（通常表示为索引）上定义分布。因此需要两个过程：把字符串编码成 token，以及把 token 解码回字符串。Tokenizer 应能完成往返（round trip）；如果不能往返，就有问题。

讲师展示了不同 tokenizer 的一些现象：

- 一个词和它前面带空格的版本可能是不同 token；很多 token 实际是“空格+词”。
- `hello` 与带空格的 `hello` 可能是两个完全不同的索引，彼此没有关系。
- 数字有时每隔几位一个 token，有时可预测、有时不可预测；也有 tokenizer 让每个数字一个 token，但会增加 token 数，需要权衡。
- 讲师展示了 GPT-5 tokenizer 的编码与解码示例。

**压缩比**定义为字节数/token 数。例如一个字符串 20 字节、编码成 8 个 token，压缩比为 $20/8=2.5$ 字节/token。压缩比越大，序列越短，这是好事，因为 attention 是二次的。可以通过增大词表提高压缩比，但词表越大越稀疏；如今 tokenizer，尤其多语言 tokenizer，词表常有 10 万或 20 万 token。

接下来比较几种朴素方案。

**字符级 tokenizer**：Unicode 字符串本身是字符序列，每个字符可用 `ord` 得到整数，也能转回字符。这能往返，但 Unicode 约有 15 万字符，词表很大；很多字符很稀有，词表使用效率低；压缩比也不好，序列仍很长，很多索引很少使用。

**字节级 tokenizer**：把字符串转成 UTF-8 字节序列，所有数在 0—255 之间。词表小，但序列更长，压缩比为 1，也不理想。

**词级 tokenizer**：按空格或正则把字符串切成 chunk，每个 chunk 作为一个 token。优点是 token 有意义，因为人类发明的词通常有稳定语义；缺点是词表是训练数据中不同 chunk 的数量，可能非常大，甚至无界：测试时遇到没见过的词只能分配 `UNK`，这会破坏 perplexity 计算。

因此需要 BPE。

## BPE 算法：数据驱动的合并 [72:55 - 76:00]

BPE 最早用于数据压缩，远早于语言模型；后来被引入 NLP 做神经机器翻译；GPT-2 是首个将 BPE 用于语言模型的论文。其基本思想是：在原始文本上训练 tokenizer，构造适合数据的词表；常见序列成为一个 token，稀有序列拆成更小单元，而不是使用 `UNK`。

算法概念上很简单：

1. 从字节序列开始，每个字节是一个 token。
2. 统计相邻 token 对的出现频率。
3. 合并出现最频繁的相邻对，创建一个新 token，加入词表。
4. 用新 token 替换序列中所有该相邻对。
5. 重复上述过程。

讲师用 `the cat in the hat` 演示：初始为字节序列；`116 104`（即 `t`、`h`）出现两次，是最频繁对之一；合并后创建 token `256` 表示 `th`，替换所有 `116 104`。下一轮把 `256` 和 `101` 合并为 `257`，再合并得到 `258`。随着迭代，序列变短，词表变大。这个玩具例子的压缩比约为 1.5。

训练好 tokenizer 后，编码新文本时，按学到的合并顺序应用这些 merge，就能得到 token 序列；解码则还原字符串。讲师快速演示了 `the quick brown fox` 的编码与解码往返。

## BPE 实现优化与分词总结 [76:00 - 78:58]

讲师给出的 BPE 实现是正确的，但非常慢。当前 `encode` 会遍历所有 merge，而 merge 数量约等于词表大小减去 256，因此效率很低。作业一会要求优化：

- 只遍历真正相关的 merge，并建立索引来加速。
- 处理 special tokens；概念不深，但对现代 tokenizer 很重要。
- 不要对整个字符串一次性分词，而是先把文本切成 chunk，再对每个 chunk 应用 tokenizer，这样更快。
- 如果 Python 不够快，可以用 Rust、C 等语言实现。

**总结：**

- Tokenizer 在字符串与 token/索引之间转换。
- 字符级、字节级、词级方案各有明显缺陷。
- BPE 是数据驱动的有效启发式方法。

讲师最后说，即使未来不再需要分词，任何替代方案也应满足两个性质：第一，Transformer 需要操作序列的某种抽象；对视频、DNA 等低信噪比的原始单元，必须先做抽象才能建模。第二，chunk 应当是可变长度的，实现自适应计算；不能把所有字节同等对待，否则会次优。
