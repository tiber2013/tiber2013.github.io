# 从 LLM 到 Agent Skill：一条链路打通大模型底层概念

> **专题视频笔记** ｜ 讲者 马克的技术工作坊 ｜ 33 分钟 ｜ [原视频](https://www.bilibili.com/video/BV1E7wtzaEdq/)

## 核心结论

这期视频用一条链路把 AI 圈里最常见的名词串了起来：LLM 是引擎，Token 是处理单位，Context 是临时工作区，Prompt 是指令，Tool 是外部能力，MCP 是工具接入标准，Agent 是能自主规划的执行者，Agent Skill 则是把私人规则写成说明书交给 Agent。它们不是并列的新概念，而是层层依赖的关系。理解这条链路，再去看 Claude Code、Codex 等产品，就不会被名词吓住。

可以把整条链路压缩成一行：

`LLM → Token → Context → Prompt → Tool → MCP → Agent → Agent Skill`

---

## 一、LLM：整个体系的地基 [00:26 - 01:53]

LLM 的全称是 **Large Language Model**，中文叫**大语言模型**，也就是大家常说的“大模型”。

现在几乎所有大模型都建立在 **Transformer** 这套架构之上。Transformer 最早由 Google 团队在 2017 年提出，对应的论文就是《Attention Is All You Need》。视频里有个形象的说法：Google 发明了火种，但真正把火点燃、引爆全世界的是 OpenAI——2022 年底 ChatGPT（GPT-3.5 一代）横空出世，2023 年 3 月 GPT-4 发布，把能力又拉高了一截。视频还提到，如今 GPT-5.4 仍是业界标杆之一，但 Claude、Gemini 等后起之秀也已经在各自擅长的领域同台竞争。

![Transformer 模型架构图与《Attention Is All You Need》论文首页对照](/coursenotes/topics/from-llm-to-agent-skill/kf_0001_00-01-05.jpg)

这一节不展开 Transformer 的内部结构，只需要建立一个认知：**大模型的底层引擎就是 Transformer**。

## 二、大模型怎么回答：一次只预测下一个 Token [01:53 - 03:05]

大模型的工作方式本质上是一个“文字接龙”游戏。

假设你问它“马克的视频怎么样”，它接收到这句话后，会在内部运算，预测下一个概率最高的词，比如“特别”。关键点来了：模型输出“特别”之后不会停下来，而是把这个刚生成的词**追加到输入后面**，再拿着新的输入预测下一个字，比如“得”；再把“得”塞回去，预测“棒”。等它认为话说完了，就输出一个特殊的结束标识，整个回答结束。

![用户提问与大模型返回答案“特别得棒”的完整交互流程图](/coursenotes/topics/from-llm-to-agent-skill/kf_0002_00-02-43.jpg)

这也解释了一个常见现象：**为什么大模型是一个词一个词地往外蹦答案**——因为它本来就是这么运作的。

## 三、Token 与 Tokenizer：模型只认识数字 [03:05 - 08:14]

前面说的“一个词一个词”其实是为了方便理解而简化的链路。真实情况是：大模型本质上是一个庞大的数学函数，内部跑的全是矩阵运算，它接收的是数字，输出的也是数字，根本不认识人类写的文字。

所以在人和模型之间需要一个“翻译官”——**Tokenizer**。它负责两件事：

- **编码（Encode）**：把文字变成数字；
- **解码（Decode）**：把数字还原成文字。

编码分两步：

1. **切分**：把输入拆成一个个最小片段，这些片段就叫 **Token**；
2. **映射**：把每个 Token 对应到一个数字，这个数字叫 **Token ID**。

Token 和 Token ID 是一一绑定的：Token 是文字形式，Token ID 是数字形式，本质上表示同一个东西。解码则只有一步——把 Token ID 映射回 Token，不需要再切分，因为模型每次只给出一个 Token。

![Tokenization编码过程示意图，展示分词与映射为数字ID的流程](/coursenotes/topics/from-llm-to-agent-skill/kf_0003_00-04-20.jpg)

| 阶段 | 做什么 | 方向 |
|---|---|---|
| 编码 | 切分 + 映射为 Token ID | 文字 → 数字 |
| 解码 | Token ID 映射回文字 | 数字 → 文字 |

**Token 才是大模型处理文本的最基本单位。** 模型一个 Token 一个 Token 地接收输入，再一个 Token 一个 Token 地输出结果。

![Token概念定义幻灯片，说明Token是大模型处理文本的最基本单位](/coursenotes/topics/from-llm-to-agent-skill/kf_0004_00-05-25.jpg)

一个很容易踩的坑是：**Token 不等于词**。视频里的例子是，“马克的视频怎么样”刚好被切成 4 个 Token，每个 Token 看起来正好对应一个词，但这只是巧合。换成“马克的技术工作坊”，按词来数是 4 个词，实际却被切成 **5 个 Token、8 个字符**；再比如“程序员”是一个完整的词，也会被拆成“程序”和“员”两个 Token。

![分词演示界面：输入“马克的技术工作坊”显示为5个Token、8个字符，下方用不同颜色标注每个Token的切分](/coursenotes/topics/from-llm-to-agent-skill/kf_0005_00-06-30.jpg)

英文也一样：Hello、going 这类常见单词通常是 1 个 Token，但并非绝对；有些单词会被拆成多个 Token，甚至某些字符需要用多个 Token 表示。所以更准确的理解是：**Token 是模型自己学会的一套文本切分规则，切出来的每一块就是它一次能处理的最小单位。**

视频给了一个便于估算的换算：

- 1 个 Token ≈ 0.75 个英文单词；
- 1 个 Token ≈ 1.5～2 个汉字；
- 40 万个 Token ≈ 30 万个英文单词，或 60～80 万个汉字。

## 四、Context 与上下文窗口：模型的临时工作区 [08:14 - 10:48]

我们平时和大模型聊天，它好像能记住之前说过的话：开头告诉它“我叫马克”，聊了几轮后再问“我叫什么”，它还能答出来。

但大模型本身只是一个数学函数，并不像人一样有记忆。它之所以能“记住”，是因为**每次发送消息时，背后的程序会把之前的整段对话历史一起发给模型**。模型每次看到的都是完整的对话内容，所以才知道之前发生了什么。

![聊天界面示例展示大模型输入输出与上下文记忆](/coursenotes/topics/from-llm-to-agent-skill/kf_0007_00-08-40.jpg)

这就引出了 **Context（上下文）**：它代表大模型每次处理任务时**接收到的信息总和**。除了对话历史和用户问题，Context 里还包括：

- 模型当前已经生成的输出；
- 当前可用的工具列表；
- System Prompt（系统提示词）；
- 以及其他被放进这次请求的信息。

![Context 概念示意图，展示对话历史、用户问题、当前输出、工具列表与 System Prompt 共同构成模型接收的信息总和](/coursenotes/topics/from-llm-to-agent-skill/kf_0008_00-09-45.jpg)

可以把 Context 理解成大模型的一个**临时记忆体**：这次任务需要的信息都装在里面，任务结束就清空。

Context 能装多少东西，取决于 **Context Window（上下文窗口）**：它指的是 Context 能容纳的最大 Token 数量。比如上下文窗口是 1 万，就代表模型最多能处理 1 万个 Token。

![上下文窗口（Context Window）定义页，说明其指 Context 能容纳的最大 Token 数量](/coursenotes/topics/from-llm-to-agent-skill/kf_0009_00-10-18.jpg)

视频里说，1 万的窗口已经算很小了。现在主流大模型普遍是百万级：视频举例提到 GPT-5.4 的上下文窗口约 105 万 Token，另外两家旗舰模型约 100 万 Token。按 1 个 Token ≈ 1.5 个汉字估算，100 万 Token 差不多是 150 万汉字，整部《哈利·波特》全集都能装下。

## 五、RAG：长文档只取相关片段 [10:48 - 11:45]

一个自然的问题是：如果有一份上千页的公司产品手册，想让大模型根据手册回答用户提问，该怎么办？把整本手册每次都塞进 Context 吗？

这不是一个好方案：手册太长，即使 Context Window 装得下，成本也很难控制。

解决办法是 **RAG（Retrieval-Augmented Generation，检索增强生成）**：先从产品手册中检索出与用户问题最匹配的几个片段，只把这几个片段和问题一起发给大模型，让模型基于这些片段回答。这样模型接收到的可能只是几段话，而不是一整本书，既不受 Context Window 大小的限制，成本也低很多。

![RAG检索增强生成流程示意图：用户提问经片段检索后输入大模型](/coursenotes/topics/from-llm-to-agent-skill/kf_0010_00-11-23.jpg)

视频在这里只讲了 RAG 的作用和大致流程，没有展开检索、向量化等实现细节。

## 六、Prompt 与提示词工程：把话说明白 [11:45 - 13:33]

**Prompt（提示词）** 是大模型接收的具体问题或指令。比如你对模型说“帮我写一首诗”，这句话就是 Prompt。它并不神秘，就是给模型的一个问题或指令；模型接到输入后才会开始运转，然后给出答案。

但问题在于：如果 Prompt 太模糊，输出就不可控。只说“帮我写一首诗”，模型可能写古诗，也可能写现代诗，甚至来一首打油诗——因为它不知道你到底想要什么。

![聊天界面中用户输入“帮我写一首诗”后模型返回打油诗的示例](/coursenotes/topics/from-llm-to-agent-skill/kf_0011_00-12-28.jpg)

一个好的 Prompt 应该**清晰、具体、明确**。比如改成：

> 请帮我写一首五言绝句，主题是秋天的落叶，风格要悲凉一点。

模型就清楚多了，生成的内容也更符合预期。

研究“怎么把话说清楚、让模型更精准地理解意图”的领域，就是 **Prompt Engineering（提示词工程）**。

![提示词工程（Prompt Engineering）章节标题页](/coursenotes/topics/from-llm-to-agent-skill/kf_0012_00-13-33.jpg)

视频作者也提到一个现象：这个领域曾经很火，但现在专门提它的人少了很多。一方面是因为门槛低，本质上就是把话说清楚；另一方面是大模型能力越来越强，即使提示词写得不够清晰，模型也能大致猜出你的意图，所以不必再在提示词上花太多功夫。

## 七、System Prompt 与 User Prompt：人设和任务分开 [13:33 - 15:10]

有些时候，我们不仅要告诉模型“要做什么”，还要告诉它“它是谁、应该按什么规则做事”。这就引出了两种 Prompt：

| 类型 | 谁来写 | 作用 | 用户是否可见 |
|---|---|---|---|
| **System Prompt**（系统提示词） | 开发者/平台在后台配置 | 设定人设、行为规则和边界 | 通常不可见 |
| **User Prompt**（用户提示词） | 用户自己输入 | 说明当前的具体任务或问题 | 可见 |

视频用“数学辅导机器人”举例：开发者可以在后台写一段 System Prompt——“你是一位耐心的数学老师，当学生问你数学问题时，不要直接给出答案，而要一步一步引导学生思考”。学生在对话框里输入“3 + 5 等于几”，这是 User Prompt。模型同时看到这两段内容后，会先遵守“数学老师”的人设，再处理具体问题，所以不会直接甩出“8”，而是引导学生自己算。

![系统提示词与用户提示词（User Prompt）的对比示例](/coursenotes/topics/from-llm-to-agent-skill/kf_0013_00-14-38.jpg)

System Prompt 约束“怎么做事”，User Prompt 说明“这次要做什么”，两者配合，模型才能既守住规矩，又完成具体需求。

## 八、Tool：给大模型接上外部能力 [15:10 - 19:19]

大模型有一个明显弱点：**无法感知外界环境**。

比如问它“今天上海的天气怎么样”，它可能会回答：抱歉，我无法获取实时天气信息，我的知识库截止到某个时间，无法提供当前天气数据。

![展示模型因知识截止日期而无法回答实时天气问题的对话界面](/coursenotes/topics/from-llm-to-agent-skill/kf_0014_00-15-43.jpg)

原因是大模型本质上只是一个“文字接龙”游戏，它根据训练数据预测下一个词，并不能真的去查天气预报网站。

**Tool（工具）** 就是用来补上这块短板的。Tool 本质上是一个**函数**：给它输入，它给你输出。比如一个天气查询工具，输入可能包含“城市”和“日期”两个参数，内部去调用气象接口，最后返回对应的天气信息。

![用户、平台、大模型与天气查询工具之间的交互时序图](/coursenotes/topics/from-llm-to-agent-skill/kf_0015_00-17-21.jpg)

一次完整的工具调用，涉及四个角色：**用户、平台、大模型、工具**。平台可以理解为一个“传话筒”兼调度员，因为用户、大模型、工具这三个角色无法直接对话，需要平台来传递信息和执行调用。

流程大致如下：

1. 用户把问题发给平台；
2. 平台把用户问题和当前可用工具列表一起发给大模型；
3. 大模型分析后决定调用某个工具，生成一条“工具调用指令”，里面包含工具名称和参数；
4. 平台收到指令后，真正调用工具背后对应的函数；
5. 工具返回结果给平台；
6. 平台把工具结果回传给大模型；
7. 大模型把结果整理成人话，交给平台，平台再返回给用户。

![平台、大模型与天气查询工具之间完整的工具调用时序图](/coursenotes/topics/from-llm-to-agent-skill/kf_0018_00-19-25.jpg)

这里最容易误解的一点是：**大模型自己无法调用工具**。它唯一的能力是输出文本；所谓“调用工具”，只是它输出了一段描述“我要调用哪个工具、参数是什么”的文本，真正执行的是平台。

各角色的职责可以这样区分：

| 角色 | 职责 |
|---|---|
| 大模型 | 选择需要调用的工具、生成工具参数、对工具结果做归纳总结 |
| 工具 | 完成具体动作，比如查询天气 |
| 平台 | 注入可用工具列表、传递信息、真正执行工具调用、串联整个流程 |

![大模型职责说明：选择需要调用的工具](/coursenotes/topics/from-llm-to-agent-skill/kf_0017_00-18-26.jpg)

所以 Tool 的本质是：**给大模型提供一套它可以调用的外部能力，让它能够感知和影响外部环境。**

## 九、MCP：工具的“Type-C”标准 [19:19 - 21:10]

工具调用还有一个工程上的大问题：工具要接入平台，平台才能把工具列表传给模型，并在模型要求时调用工具。但**每个平台的接入规范都不一样**。

同一个工具，如果接入 OpenAI，要按 OpenAI 的规范写一套；接入 Anthropic，要按 Anthropic 的规范再写一套；接入 Google，还要按 Google 的规范写第三套。同一个工具写三遍，非常浪费。

![同一工具需分别按 OpenAI、Anthropic、Google 三家接入规范重复适配的问题示意图](/coursenotes/topics/from-llm-to-agent-skill/kf_0019_00-20-03.jpg)

于是业界希望有一个统一标准：工具开发者只写一次，就能在所有支持该标准的平台上使用。这就是 **MCP（Model Context Protocol，模型上下文协议）** 的由来。

可以把 MCP 理解成**工具的“Type-C 接口”**：有了统一标准，工具开发者按 MCP 规范开发一次，就能被所有支持 MCP 的平台使用，不用为每家平台重复适配。

## 十、Agent：能自主规划的多步执行者 [21:10 - 24:12]

有了工具，大模型就能感知外部世界；有了 MCP，工具接入也统一了。但遇到更复杂的任务，只调用一次工具还不够。

视频举了一个例子：

> 我这里的天气怎么样？如果下雨的话，帮我查一下附近有没有卖雨伞的店。

假设可用工具有三个：

- **定位工具**：查询用户所在位置的经纬度；
- **天气工具**：根据经纬度查询天气；
- **店铺工具**：根据经纬度查询附近的店铺。

要解决这个问题，需要多次调用工具：

1. 大模型先判断：要查天气，得先知道用户在哪，于是调用定位工具；
2. 平台返回经纬度；
3. 大模型再调用天气工具，查询该位置的天气；
4. 平台返回天气结果，大模型发现下雨了；
5. 根据用户“下雨就找雨伞店”的要求，大模型再调用店铺工具搜索雨伞；
6. 平台返回店铺结果；
7. 大模型综合所有信息，给出最终答案。

这个过程不再是简单的“一次工具调用”，而是模型一步一步思考当前情况、决定下一步该做什么。从某种程度上说，它已经具备了一定的**自主规划能力**。

视频给出的定义是：**能够自主规划、自主调用工具、持续工作直到完成用户任务的系统，就叫 Agent。**

目前市面上比较流行的 Agent 产品包括 Claude Code、Codex、Gemini CLI 等。视频提到，这些产品的 Agent 构建模式也五花八门，并推荐了另一期专门拆解 Agent 概念、原理与构建模式的视频。

## 十一、Agent Skill：把私人规则写成一份说明书 [24:12 - 30:46]

Agent 能自主规划、调用工具，看起来很厉害了，但在实际使用中还会遇到一个新问题：**它不了解你的私人规则和输出偏好。**

比如你希望 Agent 当“出门小助手”，每次出门前帮你查天气、提醒带东西。你有自己的习惯：

- 下雨带伞；
- 光照强带帽子；
- 空气质量差戴口罩；
- 风大穿防风外套；
- 无论如何手机必带。

你还有格式要求：先来一句总结，再列出带原因的物品清单。

但在没有额外设定的情况下，你只问一句“我马上要出门，该带些什么？”，Agent 虽然会查天气，却不知道你的这些私人规则和格式要求，大概率会给你一堆废话。

为了拿到满意的结果，你每次提问都得把这一大串要求、规则、格式甚至示例全部粘贴到 Prompt 里——这显然太反人类了。

**Agent Skill 就是为解决这个问题而生的。**

### Agent Skill 是什么

Agent Skill 本质上是一份**提前塞给 Agent 的说明文档**。它通常是一个 Markdown 文件，整体结构分成两部分：

- **元数据层**：相当于这份说明文档的“封面”，告诉 Agent 这个技能叫什么、是做什么的。至少包含两个属性：`name`（技能名称）和 `description`（技能描述）。
- **指令层**：从“目标”开始，到文档结束。这一层没有固定格式，只要能把事情向 Agent 说明白就行。视频里的例子包含：目标、执行步骤、判断规则、输出格式、示例。

一个简化的 `SKILL.md` 大致长这样：

```markdown
---
name: go-out-checklist
description: 生成出门清单。当用户询问“出门要带什么/要准备什么/今天外出需要带哪些东西”时使用
---

# 目标

你是一个贴心的“出门清单助手”。你的任务是根据用户所在位置的实时天气情况，告诉用户出门必须携带的物品。

# 执行步骤

1. 调用“定位工具”，获取用户当前位置的经纬度。
2. 将经纬度作为参数，调用“天气工具”，获取降雨情况、光照强度、空气质量和风力大小。
3. 根据天气数据结果，按下方“判断规则”整理出门需要携带的物品。
4. 严格按照下方“输出格式”向用户输出最终结果。

# 判断规则

- 手机：无条件必带。
- 伞：当天气工具返回“有雨”时，必须携带。
- 帽子：当天气工具返回“光照强”时，必须携带。
- 口罩：当天气工具返回“空气质量差”时，必须携带。
- 防风外套：当天气工具返回“风大”时，必须携带。

# 输出格式

【结论一句话】
一句话总结。

【出门清单】
- 物品（原因）
```

### 怎么安装到 Claude Code

视频以 Claude Code 为例，存放位置是用户目录下的 `.claude/skills/` 文件夹。有两条硬性规定：

1. 在 `skills/` 下新建一个文件夹，**文件夹名必须与 Agent Skill 的名称相同**。例子里的技能叫 `go-out-checklist`，所以文件夹也必须叫这个名字。
2. 进入该文件夹，新建文件，**文件名必须叫 `SKILL.md`**，其中 `SKILL` 是大写。这是硬性规则，随便起别的名字系统不会认。

```text
~/.claude/skills/
└── go-out-checklist/
    └── SKILL.md
```

### Agent 怎么使用它

Claude Code 启动时会扫描 `skills/` 目录，发现新增的 Agent Skill，并读取它的**元数据层**（名称和描述）。指令层暂时不读，因为指令层内容可能比较大，全部常驻会浪费 Token。

只有当用户问题与某个 Agent Skill 的名称和描述相关时，Claude Code 才会读取对应的指令层，然后按照其中的步骤、规则和格式做事。

视频的演示中，Claude Code 识别出“出门要带什么”与 `go-out-checklist` 相关，于是加载了这个 Skill，先调用定位 MCP 工具，再调用天气 MCP 工具，最后按 Skill 要求的格式输出：

- 【结论一句话】大雨 + 光照强 + 强风，今天出门全方位挑战！
- 【出门清单】手机、伞、帽子、防风外套，并附上各自的原因。

### 还可以做什么

Agent Skill 还有一些高级能力，比如运行代码、引用资源等。但它的基础形态非常简单：**就是一份给 Agent 看的说明文档**。视频最后也提到，Skill 的按需加载方式本身就能节省大量 Token。

## 十二、要点回顾 [30:46 - 32:31]

| 概念 | 一句话理解 |
|---|---|
| **LLM** | 大语言模型，整个 AI 体系的地基 |
| **Token** | 大模型处理文本的最基本单位，不等于“词” |
| **Context** | 模型每次处理任务时接收到的信息总和，相当于临时记忆体 |
| **Context Window** | Context 最多能容纳多少 Token |
| **Prompt** | 给模型的问题或指令，分为 User Prompt 和 System Prompt |
| **Tool** | 模型可以调用的外部函数，用来感知和影响外部环境 |
| **MCP** | 统一的工具接入标准，工具写一次就能在多平台复用 |
| **Agent** | 能自主规划、调用工具、持续工作直到完成任务的系统 |
| **Agent Skill** | 给 Agent 看的说明文档，用来说明做事步骤、规则和输出格式 |

把这九个概念串起来，就是视频开头那条链路：

`LLM → Token → Context → Prompt → Tool → MCP → Agent → Agent Skill`

理解了这条链路，再去看 AI 圈里各种新产品、新技术，就更容易判断它们分别处在哪一层、解决了什么问题。
